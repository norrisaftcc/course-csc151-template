# Evaluation Rubric — CSC 151 Java Programming I

Use this rubric to evaluate the quality of a lesson, assignment, or lab. Score each category from 0 to 2.

---

## Scoring guide

### 0 — Missing or absent
The element is not present. A student or instructor reviewing the material would not find it.

### 1 — Present but incomplete
The element is present but is vague, informal, or not consistently applied.

### 2 — Complete and effective
The element is present, specific, and consistently applied.

---

## Rubric table

| Category | 0 | 1 | 2 |
|----------|---|---|---|
| **Learning goal** | Missing | General ("understands loops") | Specific and observable ("can trace a `for` loop and report final variable values") |
| **Prior knowledge** | Not addressed | Implied by topic order | Explicitly checked with a question or brief warm-up task |
| **Task progression** | One task type only | Two or three types | Learn, trace, repair/modify, build, explain, transfer — all present |
| **Execute handshake** | No gate present | Informal agreement only | All four parts confirmed: goal, constraints, prediction, success check |
| **Prediction** | Not required | Optional or suggested | Required and recorded before any execution |
| **Coach behavior** | Coach gives the answer | Coach gives broad hints | Coach uses diagnostic questions and the smallest useful hint |
| **Test evidence** | Output accepted without scrutiny | Basic test: one normal case | Three cases: normal, boundary (edge case), and failure/error |
| **Explanation** | Not required | Player describes the code | Player explains behavior, evidence, and a common mistake |
| **Role rotation** | Roles are fixed throughout | Occasional, informal switch | Structured switch with the new coach defining the next task |
| **Transfer task** | Repeats the example | Changes surface details only | Requires independent application of the concept |
| **Accessibility** | No accommodations | Some accessibility features | Alt text for diagrams, text companions for all visual content, no color-only information |
| **Respectful language** | Condescending or exclusive terms | Generally neutral | Consistently respectful, adult, and inclusive |

**Maximum score: 24**

---

## Score interpretation

| Range | Interpretation |
|-------|---------------|
| 21–24 | Strong instructional design. Ready to use. |
| 17–20 | Effective, with minor improvements available. |
| 13–16 | Usable. Revise weak gates, missing evidence, or thin transfer. |
| 9–12 | Practice tasks exist, but coaching, transfer, or evidence is weak. |
| 0–8 | Primarily task completion. Does not meet the coaching and learning standard. |

---

## Minimum acceptance criteria

An assignment or lesson must meet **all** of the following to pass minimum review:

```
Learning goal is observable.
Execution requires a complete handshake.
Prediction is recorded before execution.
Success is evaluated with specific evidence.
Player explains the result after execution.
A transfer task is included.
```

If any item is missing, the lesson does not meet the minimum standard regardless of total score.

---

## Observable goal examples

| Topic | Weak goal | Strong goal |
|-------|-----------|-------------|
| Variables | "Understand variables" | "Declare and assign an `int` variable; correctly predict its value after reassignment" |
| Loops | "Know how loops work" | "Trace a `for` loop and report the final value of the loop variable and the number of iterations" |
| Methods | "Understand method calls" | "Write a method with one parameter and a return value; call it with two different arguments and explain the difference in output" |
| Arrays | "Use arrays" | "Find the largest value in an `int` array using a single traversal without sorting" |
| Classes | "Understand objects" | "Create an instance of a class, call two methods on it, and explain the difference between the class and the object" |

---

## Checklist for self-evaluation

Use this checklist before submitting a lesson or assignment for review.

- [ ] The learning goal uses observable language ("can do," "will trace," "will write").
- [ ] The lesson checks prior knowledge before introducing new content.
- [ ] Tasks progress from trace → repair → build → explain → transfer.
- [ ] The execute-gate handshake includes goal, constraints, prediction, and success check.
- [ ] The prediction step is required, not optional.
- [ ] The coach provides a diagnostic question when the player is stuck, not the answer.
- [ ] Evidence includes at least a normal case and one edge case.
- [ ] The player explains the result after execution.
- [ ] Roles switch at least once.
- [ ] The transfer task changes a meaningful condition.
- [ ] Diagrams have text companions.
- [ ] Language is respectful and adult.
